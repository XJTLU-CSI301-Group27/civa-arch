## 版本摘要：本次已确认的业务决定

1. **数据库组织【已决定】**：采用一个统一的数据存储系统，以多个表/实体（业务域）组织菜谱、冰箱、个人/家庭计划、家庭关系、烹饪及用餐历史，而不是强制拆成三个独立物理数据库。选用本地或服务端具体技术需核对现有工程；跨设备共享数据必须有可访问的共享后端/服务。
2. **家庭计划权限【已决定】**：所有有效家庭成员可以**添加**计划项；**仅房主可删除或减少**家庭计划中的内容。权限必须在服务端或共享数据的可信写入层校验，不只是隐藏按钮。对于修改日期、换菜、增减份数等操作，需防止绕过“只有房主可删减”的规则；详见 §3.4。
3. **库存与排餐【已决定】**：库存不足**不妨碍**创建或保存菜谱、添加想吃清单、手动排餐、自动生成一天或 14 天计划；系统清晰展示缺少的食材及数量（可计算时）。
4. **库存优先推荐【建议采纳】**：在制定想吃清单、选择菜谱及自动排餐时，**默认优先展示按当前有效库存可以制作的菜**，同时始终提供“全部菜谱/缺料菜谱”入口及解除库存优先排序的选项。库存是排序信息而非资格门槛。
5. **保留原方案的重要边界**：计划 ≠ 已做饭 ≠ 已用餐；确认做饭时才按确认的用量扣除库存；个人确实吃过后才记个人食记和热量；食谱编辑不改变历史快照。

## 2 产品方向与主流程（修订）

**定位**：服务于个人及共同生活的家庭，解决“存菜谱 → 决定想吃什么 → 安排未来餐食 → 检查食材 → 确认做饭 → 记录实际用餐”的完整流程。

**首批用户**：有做饭习惯的学生合租家庭、情侣或小家庭；支持一个用户只加入一个家庭，也允许单独使用个人计划。具体账户和家庭初始化流程沿用现有实现，若不符合需做变更评估。

**两个相互关联但不同的空间**：

- **菜谱库**：公共 / 我的 / 家庭；存储“有哪些菜可以做”，不依赖当前冰箱是否有料。
- **今天（想吃清单/排餐）**：我的 / 家庭；存储“未来打算做哪些菜”，并支持手动安排或生成一天、连续 14 天计划。
- **冰箱**：单一库存视图。单人使用时对应个人可访问的库存；处于家庭时对应一个家庭的共享库存；**不在 UI 中额外分成个人冰箱和家庭冰箱两套标签**。底层仍必须有所有权/访问范围字段，防止跨家庭或跨账号串数据。
- **食记**：记录哪些菜真正做过、个人真正吃过什么及摄入量；历史数据与未来计划分离。

**推荐主流程**：

1. 用户在公共、个人、家庭菜谱中查看或创建菜谱，必要时将公共菜谱复制到个人/家庭空间并个性化修改。
2. 进入“今天”选择“我的”或“家庭”的想吃清单/排餐空间。
3. 默认先看“当前库存可做”的候选菜谱；可切换查看全部或缺料菜谱。选择时展示库存匹配及缺料清单。
4. 手动选择菜谱，或生成一天/14 天计划，先预览后确认。无论库存是否充足均可选择/保存。
5. 家庭计划共享至同一家庭成员账号；所有成员可添加，只有房主可删除或减少，操作按权限执行。
6. 确认实际做饭时核实食材用量并扣库存，写入真实烹饪记录；确认本人实际用餐后才形成个人食记、热量与历史回顾。

### 统一业务词汇

| 概念 | 含义 | 是否影响库存 |
| --- | --- | --- |
| 菜谱 Recipe | 菜的配方、食材、步骤、制作份数及来源/归属 | 否 |
| 想吃清单 Wishlist | 用户或家庭感兴趣的菜品候选，**不等同于已排日期的计划** | 否 |
| 排餐计划 MealPlan | 某天某餐准备做的菜、份数及状态 | 否 |
| 库存批次 InventoryBatch | 食材、有效数量、单位、到期日期和归属 | 由确认做饭/库存修正改变 |
| 烹饪记录 CookingEvent | 确实做过的菜、份数、执行人、时间 | 确认时扣库存一次 |
| 用餐记录 MealEntry | 某个人确实吃了什么、多少 | 不再扣食材 |

**重要区分**：想吃清单可以长期保存偏好候选；排餐计划则具有日期与餐次。即使界面都归属“今天”，数据层也应区分二者，避免收藏某道菜就自动安排到当天。原参考方案中“收藏到个人想吃清单”的行为仍然保留；家庭想吃候选是否单独持久化见 §3.2。

## 3 详细功能（修订）

### 3.1 菜谱管理：公共 / 我的 / 家庭

**三类范围【已决定】**：

| 菜谱范围 | 谁能看到 | 如何产生 | 编辑原则 |
| --- | --- | --- | --- |
| 公共菜谱 `PUBLIC` | 有权限使用公共库的用户 | 应用预置或平台公开 | 普通用户不直接修改公共原件 |
| 我的菜谱 `PERSONAL` | 拥有者本人 | 自建或从公共/家庭复制 | 个人可按口味修改副本 |
| 家庭菜谱 `HOUSEHOLD` | 本家庭有效成员 | 家庭成员新建或授权分享副本 | 遵循家庭菜谱的独立权限规则，**不可直接沿用排餐删减权限** |

- 菜谱包括：标题、图片、步骤、食材及数量单位、制作份数、预计时长、口味标签和可选热量信息。
- 即使冰箱完全为空，也允许创建、保存、编辑、搜索和收藏菜谱。
- 公共菜谱可**复制/添加到“我的菜谱”**，并产生可编辑的个人副本，避免修改公共原始内容。是否允许复制到家庭菜谱由既有团队权限确认。
- 列表支持搜索、按食材与口味筛选；保留归档而非破坏历史；“做过”应从烹饪记录推导，不以菜谱收藏替代。
- 同一菜谱可被多个清单或计划引用；删除/归档菜谱需保留计划与历史所需的快照或安全引用。
- 建议统一标准食材 ID 及别名映射，例如“番茄/西红柿”；公开图片或预置内容需明确授权。

**数据建模建议**：一张 `Recipe` 主表结合 `scope (PUBLIC/PERSONAL/HOUSEHOLD)`、`owner_user_id` / `household_id` 等范围字段，配套 `RecipeIngredient`；若现有数据模型不同，优先评估兼容迁移，不强制一刀切重构。副本记录可选 `source_recipe_id` 以标识来源，但之后独立编辑。

### 3.2 想吃清单、手动排餐与计划生成

**两个计划空间【已决定】**：

| 空间 | 可选择菜谱 | 共享范围 |
| --- | --- | --- |
| **我的** | 我的 + 家庭（当前所属家庭可访问）+ 公共 | 默认仅本人 |
| **家庭** | 家庭 + 公共 | 同一家庭的有效成员共享 |

> 个人私有菜谱默认**不直接**成为家庭排餐候选；若希望纳入，应先创建/分享为家庭菜谱副本，避免泄漏私人内容。

**候选展示与库存优先【建议采纳】**：

- 在“添加想吃”“手动选菜”“自动生成预览”等入口，默认将**当前库存可做的菜排在前面**，而不是只显示可做菜。
- 保留“全部 / 可做优先 / 仅看可做 / 缺料”筛选或排序入口；默认可以选全部菜。**“仅看可做”是用户主动选择的过滤，不影响添加或保存权限。**
- 展示每道菜所需食材与当前库存的匹配结果：`可做`、`部分食材不足`、`缺少食材`、`无法准确判断`。不能因信息不足就错误标记“可做”。
- 对缺料菜给出清单，如“鸡蛋缺 2 个、番茄缺 100 g”；若单位无法转换、保质期未知或数据缺失，应明确说明无法精确估算。
- 只统计仍可使用的库存批次，不将已过期食材计入“可做”；单位换算应有明确规则。
- 计算以菜谱选定的**计划份数**为依据。多道菜对同一库存的竞争，应在计划汇总时重新估算缺口，而不是将每道菜“单独可做”误解为全部同时可做。
- 14 天计划不能仅凭当前库存断言未来每天都可做；可显示“按目前库存估算”，同时展示总缺口并提醒库存未来可能变化。
- **绝不因缺料禁止**菜谱创建/收藏、想吃清单添加、排餐保存或生成计划；推荐优先级与操作权限分开实现。

**手动和生成规则**：

- 日期支持今天、明天、自选日期和连续 14 天；按早餐、午餐、晚餐安排，同一餐允许多道菜。
- 手动选择支持修改计划份数、锁定餐次、查看或替换候选，但家庭计划中的删除、减少、替换必须服从 §3.4 的权限校验。
- 生成前选择范围、餐次、人数、口味和时长等条件；生成 `1 天` 或 `14 天` 的候选，先进入预览，再确认写入。
- 生成方案可设“库存优先”默认排序，并支持“只按菜谱和口味生成”。无论哪种模式，缺料不应阻止生成。
- 默认保留已有计划、锁定餐次；对于普通家庭成员，如果生成结果会**覆盖、替换、删除或减少**原有家庭计划项，必须禁止该写入或改为仅填空位/新增条目，不能用“重新生成”绕过房主权限。
- 候选不足时说明原因；不自动放宽忌口限制。
- **Wishlist 与 MealPlan 分离【建议】**：想吃清单可持续积累菜谱候选；生成或手动排餐才创建具体日期/餐次。家庭想吃候选的添加、删除权限建议与家庭计划一致，但是否将家庭想吃清单独立展示，需对照现有 UI 确认。

### 3.3 冰箱库存与食材缺口

- UI 维持一个“冰箱”入口，不另设“个人冰箱/家庭冰箱”切换；底层由账号/家庭归属和授权保证隔离。
- 库存按食材、数量、单位、存放位置、到期日期和购入批次记录；同食材不同到期日分开管理。
- 支持正常、临期、过期、到期未知状态；过期批次不计为可做库存。
- 支持库存消耗、丢弃和数量修正，保留操作者及变化记录，避免负数库存。
- 与菜谱/想吃清单/排餐联动，分别显示“当前可做”“当前缺料”及可估算的缺口；缺料**只提示，不阻断制定计划**。
- 做饭时由用户先查看并确认实际用料，系统再扣库存；计划建立、添加想吃、个人实际用餐均不得直接扣除库存。
- 先统一 g、ml、个等有限单位，只做可信的同维度换算，不把“1 个番茄”无根据地自动转换成克数。
- 如果食材不足，用户仍可记录真实做饭事实，但需要明确确认库存实际消耗/修正方式，不能强制扣成负数，也不能假定所有缺口由冰箱提供。
- 首版优先实现 App 内临期提示，系统通知作为后续扩展。

### 3.4 家庭共享与权限（本次关键修订）

**新规则【已决定】**：家庭计划同步至家庭成员账号；所有有效成员均可添加计划项，只有家庭房主（`OWNER`）可以删减家庭计划内容。

| 操作 | 房主 OWNER | 普通成员 MEMBER | 说明 |
| --- | --- | --- | --- |
| 查看家庭计划 | 允许 | 允许 | 仅本家庭有效成员 |
| 向家庭计划新增菜品/餐次项 | 允许 | 允许 | 新增必须是真正的新增，不得借“新增”覆盖原项 |
| 删除家庭计划项 | 允许 | **禁止** | 客户端禁用入口，服务端也拒绝 |
| 减少原有计划项份数 | 允许 | **禁止** | 不能通过修改数量绕过 |
| 用其他菜替换既有计划项 | 允许 | **默认禁止** | 替换常等价于先删除旧项；成员可新增替代建议，是否开放无损修改待确认 |
| 修改既有计划项的日期/餐次 | 允许 | **暂不开放** | 移动可能实质删除原日期计划，需团队另定细则 |
| 增加原有计划项份数 | 允许 | **待确认** | 用户只明确所有人可“添加”；新增条目与增大份数应分开授权 |
| 锁定/解除锁定已有餐次 | 允许 | **待确认** | 涉及后续排餐权限 |
| 管理家庭成员/转让房主 | 房主负责 | 禁止 | 转让流程如未实现可列后续版本 |

**实现规则**：

1. 所有家庭共享的写操作校验 `household_id`、成员状态及角色，不能仅靠页面隐藏按钮；普通成员尝试删减时返回明确的权限错误。
2. “生成 14 天计划”“重新生成”“批量编辑”“导入模板”等操作统一调用相同的权限规则，禁止绕过。
3. 建议采用带版本号的更新或事务检查；不同成员同时添加应并存（若操作不冲突），涉及同一计划冲突时提示刷新/重新确认，不静默覆盖。
4. 保留真实跨设备共享：一台设备新增内容，其他成员刷新后可见；是否自动实时推送按当前后端能力决定。
5. 成员退出或被移除后不能继续读取或改写家庭内容；切换账号时隔离缓存。
6. 家庭菜谱、冰箱、做饭记录的修改权限**另行定义**，不要直接把“房主才可删减计划”延伸为“家庭中任何内容只能房主删除”。
7. 明确计划项状态与软删除/审计日志，以便解释谁新增、房主何时删减。若采用软删除，普通成员同样不能触发。
8. 首版联网修改；断网可查看标注时点的缓存，不承诺离线多人编辑自动合并。

**待组内确认**：家庭计划是否允许普通成员对自己刚新增、但尚未提交的本地草稿撤销？建议允许在**正式提交前**取消草稿；提交后删除仍仅限房主。这不改变已确认的共享计划权限。

### 3.5 食记日历与历史回顾

- 独立食记入口，月历支持上月、下月、选日期、回到今天。
- 有记录日期显示标记，点击查看当日早餐、午餐、晚餐和加餐。
- 支持今天记录、过去补录、编辑删除；未来日期仅做计划，不记录实际用餐。
- 从菜谱或已做菜选择，也允许记外食、临时食品。
- 记录实际份量、可选图片、备注和评价。
- 从计划进入只预填内容，本人确认实际吃了哪些、多少。
- 每人自己的用餐记录独立，家庭烹饪不自动复制成每个人吃过。
- 本周回顾扩展为选周、选月；任意历史某日从日历直接进入。

烹饪与用餐日期分开。例如周日做菜、周一吃剩菜，食记归周一，原材料扣减归周日。日期采用约定的本地日期，同步元信息采用统一时间标准。

### 3.6 热量记录

首版定位为摄入估算记录，不提供诊断或个性化医疗建议。

- 统一用 kcal；热量与卡路里是同一模块。
- 可填写整道菜总热量和产出份数，计算每份估算值，再乘实际吃的份数。
- 已知重量时可按每 100 g 的数值与实际克数计算。每条记录只采用一种计量基准，不能混用。
- 外食允许手填，标记来源为用户录入；记录估算基准和实际份量。
- 未知显示未知，不当作 0；日汇总显示“已记录 X kcal，另有 N 条未估算”。
- 只汇总本人实际用餐，不把整锅家庭用餐或未来计划计入。
- 保存食记时保存当时菜名、份量和热量快照；修改菜谱不回写历史。
- 首版不做营养库、识图估热量和减脂处方。后续引入营养数据时需保留来源和授权信息。

### 3.7 口味与已选菜推荐

- 新用户选喜欢的菜、口味和明确忌口，形成初始偏好。
- 选中一道菜后，保留已选菜，推荐其他候选或替换项。
- 先按忌口、时长等限制筛选，再考虑偏好、现有库存、临期食材和近期重复。
- 展示推荐原因，例如“符合清淡偏好”“已有两种食材”“最近较少安排”。
- 明确收藏和口味选择作为偏好，单纯浏览不直接解释为喜欢。
- 候选不足提示原因，用户主动放宽非忌口条件；不擅自放宽忌口。
- 按已知食材过滤的忌口不能保证识别全部风险；不声称推荐能保证营养均衡。

首版采用可解释规则即可，不需要训练模型或接入大模型服务。

## 4 页面与界面统一（保留既有 UI 风格）

统一五个主入口：**今天、菜谱、冰箱、食记、我的**。当前 UI 风格已确定，原则上不推翻已统一的配色、字号及导航，只调整业务层级、状态呈现和缺料提示。

| 入口 | 修订后的主要内容 |
| --- | --- |
| **今天** | “我的 / 家庭”想吃清单与排餐空间；今日餐食、1 天或 14 天生成预览、库存可做优先推荐、缺料提示、家庭计划同步 |
| **菜谱** | “公共 / 我的 / 家庭”三类库；搜索、菜谱详情、复制为个人副本、创建/编辑、做过历史 |
| **冰箱** | 单一库存入口；批次库存、到期筛选、食材缺口、录入及库存变更 |
| **食记** | 月历、确认做饭、个人实际用餐、历史记录、热量和回顾 |
| **我的** | 账户、口味偏好、家庭身份/房主管理、隐私设置 |

### 页面交互与状态要求

- 菜谱列表和选菜弹窗默认“可做优先”，显示库存匹配标签；同时提供查看全部菜谱的明确入口。
- 缺料菜的“添加想吃”“加入计划”按钮**保持可用**，点击后可展示缺料 Snackbar/提示条，但不得阻止操作。
- 生成计划先预览：显示菜品、日期、餐次、份数、当前可做状态和汇总缺料；点击确认后才写入。
- 普通成员的家庭计划项不展示/禁用删除和减少操作；若从深链或旧版本提交，后端仍拒绝并提示。
- 网络加载、空状态、操作成功、权限不足、库存数据未知分别使用统一的 UI 组件反馈。
- 导航与返回行为沿用既有约定；避免切换“我的 / 家庭”时共享状态或数据混淆。

### 防止六人形成不一致的 UI

1. 一个主工程、一套主题/导航和一组公共组件，不为新需求再建一套独立页面风格。
2. 公共组件至少涵盖标题栏、按钮、菜谱卡片、库存状态徽标、缺料详情、表单项、空状态、加载、错误反馈和确认弹窗。
3. 权限来自统一状态/接口，不能各页面手写不同的房主判断。
4. 同类业务动作采用一致的文案、成功/失败提示与动画；视觉精修不改变真实业务结果。
5. 公共数据模型、主题、导航、数据库迁移由对应负责人审查后合并。

### 平板与响应式布局

- 宽窗口可采用双栏（菜谱列表+详情、库存+批次详情、日期+选菜）；窄窗口单栏和底部导航。窗口宽度优先于设备品牌或固定横竖屏判断。
- “我的 / 家庭”、菜谱三分栏、库存排序筛选必须在横竖屏切换后保留当前选择。
- 14 天计划在窄窗口通过日期切换或按周浏览，不强塞全部餐次。
- 输入草稿、日期、筛选、滚动位置和待确认计划在合理范围内恢复；防止 Activity 重建导致重复提交。
- 大字体、键盘遮挡、系统栏、返回手势、分屏尺寸都要测试；现有原方案的平板/窄屏布局要求继续有效。

## 5 数据组织、共享接口与事务约定（修订）

### 5.1 统一数据库系统，不等于只有三张表

**【已决定】** 不将菜谱、冰箱、家庭想吃清单拆为三个互不协调的物理数据库。推荐采用**统一的数据存储系统 / 共享服务**，在业务上划分为“菜谱域、计划域、库存域、家庭与身份域、记录域”。如果现有架构已经使用本地缓存与云端服务，则应保留其职责：本地缓存可用于离线查看，家庭一致性与权限由可信服务负责。

| 实体 / 表（示意） | 作用 | 核心字段示例 |
| --- | --- | --- |
| `User`, `Preference` | 个人身份、口味、忌口 | user_id, preferences |
| `Household`, `Membership` | 家庭归属与房主/成员角色 | household_id, user_id, role, status |
| `Ingredient` | 标准食材/别名/单位 | ingredient_id, aliases, unit_type |
| `Recipe`, `RecipeIngredient` | 三类菜谱与配方用量 | recipe_id, scope, owner_user_id, household_id, ingredient_id, qty, unit, servings |
| `Wishlist`（建议） | 个人或家庭感兴趣的菜谱候选 | wishlist_id, scope, user_id/household_id, recipe_id, created_by |
| `MealPlan`, `PlanItem` | 个人/家庭按日期餐次的计划 | plan_id, scope, owner_user_id/household_id, date, meal, recipe_id, servings, version |
| `InventoryBatch` | 单一入口下可授权的库存批次 | batch_id, owner_scope/household_id, ingredient_id, qty, unit, expiry |
| `InventoryMovement` | 每次库存变化及审计 | batch_id, delta, actor_id, reason, request_id |
| `CookingEvent` | 真实烹饪确认与产出 | event_id, household_id, recipe_snapshot, servings, cooked_at |
| `MealEntry` | 个人实际用餐与热量快照 | entry_id, user_id, eaten_date, portions, kcal_snapshot |

以上是**逻辑数据模型建议**，并非已经确认的物理表结构；以现有数据库技术、迁移成本和权限机制审定字段。

### 5.2 关键约束

1. `Recipe.scope` 区分公共/个人/家庭；公共复制为个人副本后可编辑，不会回写公共原件。
2. `Wishlist` 与 `PlanItem` 分开，避免“想吃”误写成某日餐次；个人/家庭计划通过 `scope` 和对应归属 ID 隔离。
3. 统一库存视图仍需记录所有权/家庭归属，并由服务端校验家庭访问范围。
4. 同一菜谱可对应多个计划项；计划及历史引用需保证菜谱删除/修改不破坏必要的历史数据。
5. “库存可做优先”的匹配结果建议为**实时/按库存版本计算的派生数据**，避免在菜谱表冗余保存一个长期失效的 `canCook=true`。
6. 每次食材匹配考虑有效批次、单位、食谱份数与同一计划中的累计需求；无法确认时标注未知，不能默认足够。
7. 家庭计划写操作分为 `ADD`、`DELETE`、`DECREASE`、`REPLACE`、`MOVE` 等真实语义；基于修改前后的内容判断删减，**不能依赖客户端自报操作类型**。
8. 提交“确认做饭”应一次性成功或失败：保存烹饪事件、相应库存流水和扣减；用唯一请求 ID 防重复提交。个人用餐另写 `MealEntry`，不再次扣库存。
9. 共享写入包含操作者、时间、版本；并发冲突不静默覆盖，移除成员后的访问被拒绝。
10. 使用 `kcal` 表示已知估算热量；未知不视为 0。个人热量来自实际用餐记录，而不是计划或整锅产出。

### 5.3 API / 服务接口约定（逻辑契约，非现成 URL）

| 能力 | 输入 | 输出/关键校验 |
| --- | --- | --- |
| 查菜谱 | 范围、关键字、口味、用户/家庭上下文 | 本人可见菜谱、公共/家庭副本关系 |
| 库存匹配 | recipe_id、份数、库存版本 | 可做状态、已具备项、缺料项、未知项 |
| 想吃清单 | 范围、菜谱 ID、新增人 | 添加或查询相应范围的候选，不扣库存 |
| 计划生成 | 范围、日期、餐次、人数、偏好、库存排序选项 | 仅返回预览与缺料，不直接写入 |
| 确认计划 | 预览内容、目标计划版本、用户身份 | 先验证家庭角色与修改的真实含义，再原子写入 |
| 删除或减少家庭计划 | 目标项、版本、操作者 | 房主允许；普通成员权限拒绝 |
| 确认做饭 | 菜谱/用量、库存调整、唯一请求标识 | 原子扣减库存并写烹饪记录 |
| 确认个人用餐 | 用餐日期、餐次、份量、热量快照 | 只写个人记录，不二次扣库存 |

### 5.4 最重要的数据流

```text

         │
         ▼
我的 / 家庭想吃候选 ──► 手动排餐或生成 1/14 天预览
         ▲                           │
         │                           ├──► 展示缺料，但允许保存
    冰箱有效库存 ──► 可做优先排序 ────┘
                                     │
                                     ▼
                             个人/家庭排餐计划
                                     │
                             实际做饭并核实用量
                                     │
                    ┌────────────────┴─────────────┐
                    ▼                              ▼
              烹饪记录                       库存扣减流水
                    │
              个人确认实际用餐
                    │
                    ▼
              个人食记与热量历史
```

**任何环节都不能把“库存不足”转变为“禁止保存菜谱/想吃/计划”的硬性限制。**

### V2 增量职责与协同约定

- **A（工程和 UI）**：在既有主题基础上接入双空间选择、状态提示和权限交互，不重复维护业务数据。

所有组员按照当前实际责任人映射执行；上述 A–F 对应原参考方案，不应覆盖已完成的真实贡献记录。

## 7 协作与 AI 编码约定

- 一个主工程，各功能独立分支，小步合并，主分支保持能构建。
- 每天或每两天集成，定期由不同模块负责人跑完整流程。
- 共享模型、主题、导航、依赖、迁移变更由指定负责人检查。
- 可以先用模拟数据做页面，但与真实实现遵守同一接口，联调必须明确切到真实数据。
- 合并说明包含功能、截图、验证步骤、共享文件变化，由另一成员检查。
- A 建立 docs/UI_RULES.md，F 建立 docs/DATA_CONTRACT.md，全组共同维护。

在老师确认允许的编码范围内，给每次 AI 编码任务附上统一约束：

“在现有 Android 工程实现本任务，遵守 docs/UI_RULES.md 和 docs/DATA_CONTRACT.md，复用现有组件与数据接口。只修改指定业务目录；新增依赖或修改主题、根导航、共享字段、数据库结构时先提出变更。说明验证步骤和未实现部分，不另建工程或复制一套全局组件。”

AI 代码仍由负责人理解、验证和维护，生成数量不等于贡献。设计、报告、演示的课程限制见第 1 节。

## 8 首版范围与开发顺序

首版目标维持原有七类需求的合理深度，并加入本次确定的产品规则：三类菜谱范围、个人/家庭排餐空间、默认库存可做优先但缺料不阻断、房主独有家庭计划删减权。其余如批次库存、真实双设备共享、历史食记和热量仍保留。**由于 App 已基本完成，应首先核查当前代码与目标的差异，不把全部 V2 需求视为已实现或必须重写。**

稳定后再加：购物清单、系统通知、家人投票、更多营养指标和图表。

首版排除：拍照识菜估热量、全网抓菜谱、大模型生成健康处方、复杂社交、多家庭切换、断网多人编辑自动合并。

### 待执行的关键验收（须增加 V2 测试）

- 明天的计划不增加今天食记与热量。

- 三台设备同一版本运行；宽窄窗口、横竖屏切换时不丢已选日期或重复提交。
- 共享计划在三账号间一致，但个人食记与热量不自动串到其他账号。


### V2 必增验收用例

1. 冰箱为空时仍能创建菜谱、收藏想吃、手动排餐与生成一天/14 天计划，缺料清单正确显示。
2. 默认候选先展示当前库存可做的菜；切换“全部”后，缺料菜仍可选择。
3. 某菜谱单独可做但两道菜合计超出库存时，汇总计划正确提示缺料。
4. 个人计划能选个人+家庭+公共菜谱；家庭计划只列家庭+公共菜谱；个人私有菜谱不会被家庭用户意外看到。
5. 普通家庭成员可新增家庭计划项，其他设备刷新可见。
6. 普通成员无法删除、减少份数、替换/移动旧项或通过“重新生成”覆盖旧项；房主可删减。
7. 直接构造未授权请求仍被服务端拒绝，不能只通过隐藏按钮通过测试。
8. 确认计划不扣库存；确认做饭只扣一次；个人记录摄入不重复扣库存。
9. 公开菜谱复制到个人后可以修改，而公共原件和其他用户副本保持不变。

## 9 三台小米平板的开发与验收安排

### 9.1 设备登记与首次运行

先用 P1、P2、P3 命名，无需收集私人设备序列号。以下字段待实际填写，不虚构参数。

| 设备 | 型号 | Android 版本 | MIUI/HyperOS 版本 | 可用空间 | 窗口与方向 | 保管配对 |
| --- | --- | --- | --- | --- | --- | --- |
| P1 | 待登记 | 待登记 | 待登记 | 待检查 | 竖屏、横屏、可用分屏 | A/B |
| P2 | 待登记 | 待登记 | 待登记 | 待检查 | 竖屏、横屏、可用分屏 | C/F |
| P3 | 待登记 | 待登记 | 待登记 | 待检查 | 竖屏、横屏、可用分屏 | D/E |

首轮流程：登记信息 → 在设备允许的情况下开启开发者选项及 USB 调试 → 连接并授权开发电脑 → Android Studio 识别设备 → 安装并运行测试包 → 记录构建版本与结果。不同系统的设置路径以实机为准；当前尚未连接设备，也未执行这些检查。

开发者选项、驱动或安装授权遇到阻碍时先记录实际报错，再针对设备和电脑排查。不要为方便调试关闭屏幕锁或使用私人主账号作为演示账号。照片首版允许从系统选取演示图片，相机直拍可后置，减少权限与适配工作。

### 9.2 三账号角色与测试阶段

| 设备 | 测试账号 | 阶段一 | 阶段二 |
| --- | --- | --- | --- |
| P1 | user_a | 创建家庭并作为管理员 | 维护共享计划，保留本人食记 |
| P2 | user_b | 受邀加入同一家庭 | 修改库存、参与做饭并记录本人摄入 |
| P3 | user_c | 未加入家庭，验证不能读取 P1/P2 数据 | 接受邀请后验证同步；之后再验证移除权限 |

设备不绑定产品权限，角色来自账号与家庭成员关系；换设备登录仍须得到同样的权限结果。三台设备够展示三人协作，六名组员不需要六台设备才能验证贡献。

### 9.3 网络与共享边界

同一 Wi-Fi 不能自动产生数据同步，三台平板必须访问同一共享服务。共享服务不应只运行在某台平板上；演示前确认账号、服务和网络可用。

若演示服务运行在开发电脑上，平板访问的是电脑在局域网中的可达地址，不能填 localhost；确认同网段、端口和防火墙规则，且只开放必要访问。若采用远程服务，则确认现场能访问，不能把“能上网”当作目标服务一定可达。

优先完成在线共享，界面先采用进入页刷新或显式刷新并展示状态；自动实时更新作为稳定后的增强。不承诺尚未验证的毫秒级同步。断网演示明确区分“缓存可查看”与“共享写入暂停”，不使用手工导入数据冒充同步。

### 9.4 核心测试矩阵

| 场景 | 三台设备如何操作 | 预期与证据 |
| --- | --- | --- |
| 入组权限 | P1 建家庭，P2 加入，P3 暂不加入 | P2 能访问共享内容；P3 的请求被拒绝，记录实际结果 |
| 排餐同步 | P1 修改明日晚餐，P2/P3 入组后刷新 | 三台看到一致菜谱、日期和份数；记录更新时间 |
| 并发编辑 | P1/P2 从相同旧版本提交不同改动 | 第二次发现冲突，提示刷新确认，不静默覆盖 |
| 库存与重试 | P2 确认做饭，重复点击或重试；其他设备刷新 | 只产生一次库存扣减和烹饪记录 |
| 个人摄入 | 三账号各记录不同份量 | 本人食记与热量独立，共享烹饪只保存一次 |
| 断网恢复 | P3 断网，P1 改计划，P3 恢复并刷新 | 断网有提示，恢复后取得新数据，无离线假提交 |
| 权限撤销 | P1 移除 P3，P3 再请求共享数据 | 新请求拒绝，订阅停止，客户端清理共享缓存；不声称能远程抹除已导出的资料 |
| 布局与键盘 | 每台切横竖屏、可用分屏、放大字体并输入长文本 | 核心操作可见，状态保留，不重复写入 |
| 生命周期 | 编辑时切后台、锁屏再恢复；在受控情况下测试进程重建 | 按已声明规则恢复草稿或提示恢复，不误确认做饭 |
| 升级与重装 | 安装新测试包；单独测试全新安装 | 升级行为明确；服务端数据重新登录可取回，本地未同步草稿不承诺保留 |

每条记录设备、构建版本、账号角色、前置数据、步骤、预期、实际、截图或日志及复测结果。不要在报告中把本表直接作为已通过的结果。

三台同品牌设备不能证明所有 Android 设备兼容。日常仍用至少一个手机尺寸模拟器检查窄屏，设备系统版本相同时补充其他目标版本的模拟器检查；目标版本范围等登记完设备并确定构建配置后再定。

### 9.5 演示与版本纪律

- 每个集成版本生成相同版本标识的安装包，三台均核对版本，避免把版本差异误判为同步问题。
- 准备专用测试账号和可恢复的演示数据；清楚区分测试环境与个人资料。重置前确认不会删除成员私人内容。
- 每周至少安排一次三机联调，由对应业务负责人修复问题，不单设一个只测试却不编码的人。
- 演示时 P1 展示排餐，P2 展示库存及烹饪确认，P3 展示个人食记和历史；现场操作要遵循同一个使用流程。
- 演示前检查充电、网络、通知、服务状态和三台版本；可准备热点与备用安装包，网络备选路径需要事先实测。
- 首版不新增推送通知依赖；若后续做后台提醒，再针对实机系统设置验证，不预先假设小米系统必然阻止或允许。

## 11 新旧方案差异与待确认决策

| 主题 | 原参考方案 | V2 确定或建议 | 当前落地注意事项 |
| --- | --- | --- | --- |
| 数据库 | 按多个业务实体规划 | 统一存储系统，按业务实体/表组织【已决定】 | 不等于所有信息保存在一个本地文件；家庭共享仍需可信后端 |
| 菜谱 | 共享菜谱与个人收藏为主 | 公共/我的/家庭三范围【已决定】 | 检查旧菜谱迁移、复制副本与可见范围 |
| 排餐 | 家庭计划为主 | 我的/家庭双空间【已决定】 | 检查个人私有计划的权限隔离 |
| 家庭权限 | 成员可编辑计划 | 成员可加，房主才可删减【已决定】 | 修改、替换、批量生成都不得绕过 |

| 食记 | 区分做饭和用餐 | 保留 | 不把家庭做饭自动当作每人实际摄入 |

### 必须由团队明确的未决问题

- **普通成员是否能增加已有计划项的份数？** 当前建议先只允许新增独立条目，增份权限另定。
- **普通成员是否能修改已有计划项备注/日期/锁定状态？** 当前默认仅新增、不删减；所有可能导致原项减少/消失的变更先禁用。
- **家庭想吃候选是否需要独立于家庭排餐计划保存？** 建议需要，但如果当前 UI 把两者合并，需先评估数据库迁移和用户理解成本。
- **公共菜谱由谁提供和维护？** 必须确定内容来源、编辑权与版权责任。
- **单人模式如何对应统一库存？** 可使用一个归属于账户的库存空间，创建/加入家庭后是否迁移既有食材需单独决定，不能自动混用。
- **库存不足时实际已做饭如何处理？** 建议记录实际烹饪事实，同时引导用户确认补录/修正库存，而不是允许负库存。
- **房主权限转移和家庭退出**：现阶段若未实现，明确限制并提供合理提示。
