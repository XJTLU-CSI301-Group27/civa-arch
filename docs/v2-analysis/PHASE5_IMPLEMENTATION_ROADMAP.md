## 5.2 任务详细卡（P0 与关键 P1）

### T-01 家庭菜谱 update 事务化

| 项 | 内容 |
| --- | --- |
| **目标** | 更新家庭菜谱时，`UPDATE recipes` / `DELETE recipe_ingredients` / `INSERT` 要么全成功要么全失败 |
| **修改内容** | 用 `transactions.execute(...)` 包裹 `HouseholdRecipeService.update` 的三步；在同一事务内返回结果 |
| **涉及文件** | `server/.../recipe/HouseholdRecipeService.java`（1 个文件） |
| **前置依赖** | 无 |
| **风险** | 低。不改契约、不改行为，只加事务边界 |
| **测试标准** | 新增集成测试：构造重复 `ingredientId` 的 update → 请求失败且原 `recipe_ingredients` 完整、`version` 未递增；正常 update 仍成功 |
| **完成条件** | 测试通过 + `server test` 全绿 + 无契约变化 |
| **对应差距** | G-06 |

### T-03 确认做饭校验强化

| 项 | 内容 |
| --- | --- |
| **目标** | "确认做饭"必须按确认的用量准确扣减：不能空扣、不能扣错配料、不能扣过期批次 |
| **修改内容** | ①校验每个 `trackStock=true` 配料都有分配且合计 = 需求（`CEILING` 3 位）②`deduct` 校验 `batch.ingredient_id` 与 `unit` 与分配一致 ③过期批次 → `EXPIRED_BATCH` ④`expectedVersion` 缺失 → 400 ⑤错误码统一 |
| **涉及文件** | `server/.../record/CookingEventService.java`、`RecordsErrors.java`、`CookingEventHttpIntegrationTest.java` |
| **前置依赖** | 无（客户端本来就提交 preview 的完整 allocations） |
| **风险** | 中。收紧后"部分分配"会被拒；需确认客户端两个入口都提交完整分配（当前是） |
| **测试标准** | 空数组 → 拒绝；少分配 → 拒绝；错配料批次 → 拒绝；过期批次 → 409；正常路径成功；重试只扣一次 |
| **完成条件** | 5 个新测试 + 既有烹饪测试全绿 |
| **对应差距** | G-05 |

- P1 全部（T-14..T-23）= **约 11–13 人日**。
- 合计 **20–24 人日 > 可用**。

| **M · 推荐** | S + Batch 5（T-17/T-18/T-19）+ Batch 7（T-22/T-23） | ~18–21 | 覆盖 V2 §3.1/3.2/3.3/3.4 主体；缺 1/14 天自动生成 | 中；需并行，测试时间被压缩 |

### 推荐
**M，并把 T-20/T-21（生成）标为"如果 12/03 前 M 全部完成且测试全绿，才做"**。理由：
- 生成是 V2 §3.2 的一部分，但它依赖权限 + 可做状态 + 未验证的 commitPlan，是"最后 20% 吃掉 50% 时间"的典型；

必须在报告中明确列出未实现项（生成、个人计划跨来源、公共菜谱直接进家庭计划），并说明这是时间约束下的显式裁剪，不声称已完成。
