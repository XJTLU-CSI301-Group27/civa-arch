## 2.2 五个重点业务变化的深度解读

### 2.2.1 Recipe Management（§3.1）

**V2 真正要求的不是"加一个 scope 字段"，而是四件可验证的事：**

1. 用户能明确知道自己在看/编辑哪个库，且三库的**权限语义不同**（公共只读、个人独享、家庭共享）。
2. 复制是**单向、可编辑、不回写**：公共原件与其他用户的副本不受影响（QA-09）。
3. 库存与菜谱**彻底解耦**：空冰箱、缺料、单位不匹配、食材未知，都不能阻止创建/保存/编辑/搜索/收藏（RCP-02）。
4. 归档要能"找得回来"，"做过"必须来自烹饪记录而不是收藏（RCP-09）。

**本工程的含义**：三张表已经满足"三个范围"，但存在三处结构性不一致需要正视——
- 食材表示不一致（公共/个人 = 自由文本 JSON；家庭 = 标准 `ingredient_id` + 数量 + 单位）；
- 字段集不一致（家庭无 description/flavors，个人无 tags，公共无 version/archived）；
- 跨范围引用能力不一致（只有"想吃"是多态，计划/做饭/食记都只能指向家庭菜谱）。
V2 允许"优先评估兼容迁移，不强制一刀切重构"，因此**不建议合并三张表**；建议补"跨范围引用 + 来源追踪 + 字段对齐"这三类增量。

**不得自行决定**：是否允许公共菜谱复制到家庭菜谱（PD-10）；公共内容来源与授权（PD-05）。

---

### 2.2.2 Personal & Household Meal Planning（§3.2）

**两个空间的关键差异（必须落到数据层，不能只在 UI 上切换）：**

| 维度 | 我的计划 | 家庭计划 |
| --- | --- | --- |
| 候选池 | 公共 + 个人 + 当前家庭 | 公共 + 家庭 |
| 可见范围 | 仅本人 | 本家庭有效成员 |
| 写入权限 | 本人 | 成员可新增；房主可删减 |
| 共享方式 | 无（默认不上服务端） | 服务端共享 + 刷新可见 |
| 库存影响 | 无 | 无 |

**V2 明确要求实现的"新增 vs 删减"语义**，本质是一个**服务端 diff 判定问题**：

> 收到一次写入（整槽 replace 或批量 commit）后，服务端必须比较"该槽原有 items"与"提交后 items"，识别出：
> - `ADD`（原集合里没有的新 recipeId）
> - `DELETE`（消失的 recipeId）
> - `DECREASE`（同一 recipeId 份数变小）
> - `REPLACE`（删 A 加 B，等价于先删后加）
> - `MOVE`（同一 recipeId 从 A 日/餐移到 B 日/餐）
> - `INCREASE`（份数变大，PD-01 待确认）
>
> 然后对 `DELETE / DECREASE / REPLACE / MOVE` 检查"是否房主"，对 `ADD` 放行所有成员。**不能相信客户端传来的 operation 类型**（DAT-10）。

**当前实现的致命点**：客户端只有"整槽替换"，所以"普通成员选一道新菜"在服务端看来就是"删掉原 2 道 + 加 1 道"。如果只加"房主才能 replace"，会把 V2 明确允许的"成员新增"也一起禁掉；如果只放行 replace，则成员可以清空整槽。**必须做 diff 语义拆分，这是 P0 的核心设计点。**

**"生成 1/14 天"与权限的交叉**：成员生成时若会覆盖/替换/删除既有项，必须禁止该写入或降级为"只填空位 + 追加"。落锁槽必须保留。这要求生成走**与手动写入同一个服务端校验入口**。

**不得自行决定**：成员增份（PD-01）、成员改锁/备注（PD-02）、成员移动（PD-03）、家庭想吃清单独立化（PD-04）、个人计划是否上服务端（PD-12）。

---

### 2.2.3 Inventory-aware Recommendation（§3.3）

**V2 的排序模型可以精确化为四个正交维度：**

| 维度 | 取值 | 是否影响保存 |
| --- | --- | --- |
| 匹配状态 | `可做` / `部分不足` / `缺少` / `无法判断` | 不影响 |
| 展示顺序 | 可做优先（默认） / 全部（可选） | 不影响 |
| 筛选 | 全部 / 仅可做 / 缺料 | 用户主动选择，不影响"添加/保存"权限 |
| 缺口明细 | 有可计算数量的缺料清单 / "无法精确估算" | 不影响 |

**必须守住的三条反例：**

1. **未知 ≠ 可做**：公共/个人菜谱的食材是自由文本，无法映射标准食材时，匹配状态必须是"无法判断"，**不能因为"没查到缺料"就显示为可做**。
2. **单菜可做 ≠ 多菜可做**：两道菜各需 600g、库存 800g，逐菜计算都是"可做"。计划汇总必须重新按累计需求估算（STK-12 / QA-03）。
3. **今天可做 ≠ 14 天都可做**：14 天计划只能标注"按目前库存估算"，并展示总缺口，不得承诺未来可做（STK-13）。

**本工程的现实约束**：真正能计算的只有家庭菜谱（结构化食材）。公共/个人菜谱要进入匹配，必须先做"食材名 → 标准 ID"的映射，而现词典只有 26 条、映射靠子串匹配。因此 **"可做优先"的落地顺序必须是：先把家庭菜谱的匹配接进 UI（立即可做、风险低），再解决公共/个人菜谱的映射（需要词典扩充与人工确认，属于 P1/P2）**。绝不能为了"看起来有缺料提示"而把未知显示成"可做"。

**不得自行决定**：单人模式库存归属（PD-06）；缺料时做饭是否允许（PD-07）。

### 2.2.4 Database Architecture（§5）

**V2 的核心判断是"统一系统 ≠ 只有三张表"，且"如果现有方案能实现需求，不得为了架构形式重建"。**

对照结论（详见 Phase 3）：
- "一个 PostgreSQL + 按业务域分表"——**已满足** DAT-01/DAT-02。
- "表级逻辑模型能表达 14 类实体"——**基本满足**，缺口是：`Wishlist` 没有家庭维度、`MealPlan` 没有个人维度、`PlanItem` 无法引用公共菜谱、`Recipe` 没有统一 scope（分三表）。
- "权限在可信写入层"——**不满足**（无角色、无 diff 校验）。
- "历史不因菜谱编辑被改写"——**做饭满足，食记偏弱**。

**因此本阶段对数据库的立场**：
1. **不合并三张菜谱表**（成本高、收益低、V2 明确不强制）。
2. **只做加法**：`households.owner_user_id`（若 PD-11 确认）、`plan_items` 的跨范围引用（若做 PLN-04）、`wishlists` 的 scope 化（若 PD-04 确认）、`user_recipes` 的来源字段。
3. **任何表结构改动必须附**：现有模型 → 目标模型 → 表与关系 → 迁移方案 → 兼容性风险 → 对现有功能的影响（Phase 4 已按此格式给出）。
4. **不删除旧表、不删数据、不做破坏性回填**。`recipe_catalog`/`user_recipes`/`recipes` 三表并存是既有事实，迁移只增不改。

**不得自行决定**：是否合并表（V2 建议评估，不强制）；个人计划是否落库（PD-12）。

### 2.2.5 Cooking & Meal Records（§3.3、§3.5）

**六个概念的边界（V2 的核心不变量）：**

```
Recipe ──(被引用)──► Wishlist / MealPlan（都不扣库存）
                          │
                   确认做饭（用户核实用料）
                          ├──► CookingEvent（家庭维度，冻结快照）
                          └──► InventoryMovement(COOK)（扣库存，一次）
                                  │
                          本人确认实际用餐
                                  └──► MealEntry（个人维度，不再扣库存）
```

**现状的两个违规点（Phase 3 会展开）：**
1. **食记"在家吃"直接扣库存**：`DiaryFragment.consumeBatch()` 逐批 `changeInventory(CONSUME)` 后才写 `MealEntry`。这使"个人用餐"成为扣减原材料的第二条通道，违反 CKG-05/STK-10，且非原子、会把超扣夹成 0。
2. **客户端做饭幂等键不稳定**：每次点击 `UUID.randomUUID()`，超时重试会换 key，可能重复写 `cooking_events` 与重复扣库存，违反 CKG-03/QA-12。

**另外两个"看似小事但会破坏不变量"的点：**
- 服务端 `confirmCooking` 允许 `allocations=[]`，且不校验分配是否覆盖配方需求、不校验配料/单位是否匹配批次 → 可写出"做了饭但没扣库存"或"扣错配料"。
- 食记 `recipe_id` 是弱引用（菜谱删除后悬空），且不存完整快照 → 历史回看可能丢失。

**不得自行决定**：缺料时是否允许记录做饭（PD-07）。

## 2.5 Phase 2 结论摘要

1. V2 的**已确认需求**可归为 8 组、约 70 条可验证条目；其中与本工程差距最大的是 **家庭权限（PRM）** 与 **计划候选/生成（PLN）**。
