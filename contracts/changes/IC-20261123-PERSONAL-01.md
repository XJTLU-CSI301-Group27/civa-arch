## 涉及 operationId / schema

- `GET/POST /api/v1/me/recipes`：`listPersonalRecipes`、`createPersonalRecipe`
- `GET/PUT/DELETE /api/v1/me/recipes/{recipeId}`：`getPersonalRecipe`、`updatePersonalRecipe`、`deletePersonalRecipe`
- `PUT /api/v1/me/recipes/{recipeId}/archive`：`setPersonalRecipeArchived`
- schema：`PersonalRecipe`、`PersonalRecipePage`、`PersonalRecipeIngredient`、
  `CreatePersonalRecipeRequest`、`UpdatePersonalRecipeRequest`、`ArchivePersonalRecipeRequest`

## 原需求及复用现有接口的评估

产品要求用户自建菜谱"跟账号走"，与家庭菜谱、公共菜谱三者互不混淆。现有 `recipes` 表要求
`household_id NOT NULL` 且食材引用标准食材 ID，无法表达"个人、跨家庭、自由文本食材"的菜谱；
`wishlists` 也仅覆盖家庭菜谱。因此新增个人菜谱资源（`/me/recipes`），食材沿用公共目录的自由文本
结构 `PersonalRecipeIngredient`，家庭菜谱（后续）再走既有 household 接口并强制标准食材 ID。

## 旧接口与新接口

- 旧：本地 `RecipeStore`（SharedPreferences）或家庭菜谱接口，均不满足"个人跨设备"。
- 新：个人菜谱按 `user_id` 归属；`update/delete/archive` 使用 `expectedVersion` 乐观并发；
  创建使用 `Idempotency-Key`；食材/步骤保持自由文本，未知营养保持 null。

## 影响调用方、数据库、缓存及 UI

- 客户端：菜谱 Tab「我的」来源、个人菜谱编辑器、公共详情「保存到我的菜谱」、家庭添加时的个人快照（P3）。
- 数据库：新增 `user_recipes` 表（无家庭外键，删除账号即删）。
- 缓存：客户端只读缓存；写操作直连服务端。

## 兼容性判断及未验证项

- 兼容：纯新增；既有 45 个 operation 未改动（已逐 operation 对比）。
- 未验证：多设备同时编辑的冲突提示体验（依赖 expectedVersion，P2 后段验证）。

## 决定

采用：新增个人菜谱资源。决定者：项目负责人（2026-11-23 计划评审通过 P2）。
